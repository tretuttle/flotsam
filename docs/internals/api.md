# Extension API and the export host

Extension pages call one API, `browser.oneClickHar`, defined by one table in `apps/extension/experiment/contract.ts`. The experiment host runs it in the parent process with the system principal. Pages hold the `moz-extension` principal and get counts, rows and job states back: no file path, body byte or HAR text crosses in either direction. Content principals reach nothing.

## One table, a parser on every parameter

- Every parameter carries its own parser, and `createOneClickHarApi` runs `parseArguments` before any handler, in every host. Gecko's schema checks the experiment host's integers too, but the standard host's port has none, so the parser is the check that always runs. Object parameters are `any` in the generated `schema.json` and checked only by their parser: `getPopup({ tabId: -1 })` is refused by the parser, `getEnvironment(-1)` by the schema first.
- `contract.test.ts` walks every row's parameter and result types and fails typecheck when a key that holds a path, folder, text, content or HAR, or a byte array, appears at any depth. A key under an index signature is walked too: `string` keys swallowed a planted `folder.path` until the walk skipped them.
- Pages may import only `experiment/contract.ts`; a lint override on `apps/extension/src/**` refuses the rest.

## Tab ids are states

`tabManager.get` throws for tab 0, a closed tab, an unknown id and a private tab this add-on may not see. The host looks a tab up once and turns any throw into `no-such-tab`, so `getEnvironment` and `getPopup` answer every parsed id with a state. `{ tabId: null }` is the popup's own "no tab" (Zen's empty tab reports -1).

## Counts and exports read the same lines

- The activity index is filled at startup from every valid segment summary, after recovery summarized earlier runs, and then from each batch of lines the store appends. Both the popup and an export flush the store twice first: a file body's line joins a batch only after its rename, which runs on the write chain after the first flush was queued. The popup's count for a preset therefore equals the entries the export writes, live captures included.
- An export reads the segments `segmentsFor` names, keeps the lines `inSelection` accepts, and adds the recorder's live captures as in progress. Bodies are read from packs and body files in 3 MiB chunks; a stored wire encoding is undone by Gecko's own converters (`gzip`, `deflate`, `br`, `zstd`), so `content.size` is the decoded size.

## The file

- One export runs at a time, and it keeps running after the popup closes. `listExports` keeps this run's ten newest jobs.
- The file goes to the chosen folder or the browser's Downloads folder.
- **The rule:** an export never overwrites, deletes, renames or leaves bytes in a file it did not create, and never reports `done` for a file it did not write. A check of a path followed by a call on that path cannot keep it, because another process can swap the path between the two; six review rounds closed such windows one at a time. So the export acts on objects it holds, not on paths:

  | Platform                                                | Folder                                                                                  | The export's file                                                                      | Finishing                                                                                                                                                            | Failure, cancel, crash                                                          |
  | ------------------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
  | Linux (x86-64, aarch64)                                 | held as a directory descriptor (`O_DIRECTORY \| O_NOFOLLOW`), and its path must name it | unnamed in the held folder (`O_TMPFILE`), written and read only through its descriptor | `linkat` of `/proc/self/fd/<n>` into the held folder: names exactly that inode, and fails `EEXIST` rather than replace, so a taken name moves on to `<name> (2).har` | closing the descriptor ends an unnamed file; nothing is ever renamed or deleted |
  | Windows, macOS, a Linux file system with no `O_TMPFILE` | judged by its real path                                                                 | `<name>.har.part`, created exclusively                                                 | `IOUtils.move(..., { noOverwrite: true })`, which checks and then renames                                                                                            | the part is deleted or moved back by path                                       |

  The Linux calls run in `file-worker.ts`, a ChromeWorker using js-ctypes (Gecko has no unnamed-file or link call), so a call stuck in the kernel stalls that worker, not the main thread, and still ends the export `timed-out`. The parent script starts it from `resource://one-click-har/`, a substitution for the add-on's own package that grants no content access. `IOUtils.move`'s `noOverwrite` checks before it renames, so on the second row a file put at the finished name in between is overwritten; that row does not meet the rule, and Windows needs its own by-handle calls (`SetFileInformationByHandle` with `FileRenameInfo` and `ReplaceIfExists` false, and `FileDispositionInfo`), not built yet.

- On Linux, before the link the unnamed file must hold the written length and first bytes, and the held folder must still be at the folder's path. After it, the folder must still be there, the finished name must be the unnamed file's own device and inode, and the file must still hold what was written. A failure after the link leaves the export's own named file where the link put it, inside the held folder wherever it was moved, and the job reports it as `kept`; a cancel that arrives after the link is reported in the job's audit. A kill leaves nothing: no name was ever given, so there is nothing to journal or recover.
- Where a part is named, recovery deletes only a part it can prove the export created. The document's first bytes carry a random id (`log._harExportId`), and the sink writes that opening alone, at once. Only after the exclusive create succeeded and the opening is read back from the file does a line in the archive's `exports.jsonl` name the part, with those bytes as its head. An end line follows the rename, the delete, or the finding that the file at the path is no longer the export's. The next start deletes a part with no end line only when the file at its path is a regular file, not a link, that still starts with its head, checked again just before the delete; anything else is left and reported as `leave-export-part` (crash row 13). That read opens the path for reading and writing, which never waits on a FIFO, and reads nothing from a file shorter than the head.
- Every file call goes through `exportFiles` in `export-file.ts`; `geckoExportPlatform` in `host.ts` and `file-worker.ts` hold the only raw calls. For a named part:
  - The folder is judged by its real path. A folder that is a link, or whose real path is inside or contains the profile, the archive or a known substitution, is `folder-refused`, before anything is created in it. A missing folder is created, then judged again. The same guard runs before Linux holds the folder.
  - The part is created exclusively (`PR_EXCL`) and every byte goes through that one handle, opened for reading and writing; the export never opens the part's path again (round 4 reopened it, and a FIFO swapped in made the export wait forever). Before the journal line and the rename, the path must name the handle's file: when the handle lengthens the file by one byte, lstat of the path follows; and the handle must read back the written length and first bytes. Otherwise `file-replaced`.
  - After the rename the folder and the finished entry must still resolve to the folder resolved at start, and the finished name must follow the handle; otherwise the rename is undone and the export is `folder-refused`, `folder-missing` or `file-replaced`. A finished name gone by then is `file-replaced`: round 6 resolved a missing entry's real path, which throws in Gecko, and reported `folder-refused`.
  - A discard deletes only through a folder that is still the export's, and only the handle's own file.
- A refused call is the only failure. A folder that is gone, moved or replaced by the time a call fails is reported as that (`folder-missing`, `folder-refused`, `not-a-folder`), whatever the call threw; otherwise the kind comes from `FS_ERROR_KINDS`, keyed by the identifier the platform gives (an IOUtils `DOMException` name or an XPCOM nsresult name). Each name in the table is produced by a cause `export-failures` makes happen for real; a name no cause produces has no row and comes back `other`. A full disk is `disk-full` with both numbers whenever the volume had fewer free bytes than the call needed. Gecko's own Downloads helper falls back to the system Downloads folder when the configured one fails, so the matrix names each row's folder in `settings.json`.
- A failure is a fixed kind and numbers, with no text field. A platform error's message names the export folder and the profile (`jar:file://<profile>/extensions/...`), and the failure crosses to the `moz-extension` principal; one round sent both in `{ kind: "other", detail }`. `contract.test.ts` fails typecheck if any failure field reachable from `listExports` is not a number or its kind is not a fixed word.
- Cancel ends the job `cancelled` at once and aborts the run's signal, which `runExport` reads before every body chunk and the finish reads before naming the file, so at most one chunk (4 MiB of base64) and one sink batch are written after it.
- Every asynchronous file call is bounded at `EXPORT_STEP_MS`, 15 s, and a call still running then ends the export `timed-out`. On Linux that is every call, writes included. A Linux link that lands after the limit names the export's own file and is left; a named part's late rename is checked and cleaned up. Synchronous calls on a named part (an lstat, a write through the handle) are not bounded.
- A harness profile can hold an export before and after the link (`export-pause` on the harness topic), which is how the matrix reaches those moments: js-ctypes binds libc directly, so a preloaded library cannot hold the call. It can also force named parts (`extensions.oneClickHar.harness.namedParts`), so the matrix covers both rows of the table on Linux.
